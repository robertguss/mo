## Implemented behavior

**Service promises.** A `service` block can hold promises about the whole service. A
step promise must hold across every tool call, clock advance and crash with its
restart, and reads the state `before` and `after` and the clock `now`. A tool promise
(`promise "..." on TOOL`) must hold after every call to that tool which replied, and
also reads the tool's arguments and `reply`. Anchors stay mandatory. `mo test` judges
each one after every step of the same generated sequences as the recovery check, and a
failing promise prints its shrunk sequence with the step that broke it. A service has
at most 64. A promise on a function that takes a `Simulation` is still E1400.

**Promise strength.** `mo test FILE --strength DIR` measures how many wrong versions of
a program its intent kills. It runs the program's own promises and examples, then each
wrong version in `DIR` against the same fixed plan, and prints one `strength` record. A
wrong version that stops is kept out of the rate, and so is one that does not check or
changes a digest, unless a `counted` file lists it. A plan cut short is E1432, never a
pass.

**The intent listing and the lock.** An intent item is one promise, one service promise
or one example row. Its identity is a SHA-256 digest of its own text and of every
declaration it reads, so it changes only when what judges the code changes.
`mo intent FILE` lists a program's intent without its code, and `--against OLD` shows
what changed. Robert approves items one by one with `mo review --approve`, under a
third credential that the service refuses when it arrives with the upgrade credential.
Holding the service token and the upgrade credential approves nothing. The service
token and the two credentials must all differ, or the service does not start (E1434).
Approvals, the review setting and every decision live in the data folder, and
`mo history` prints them. An activation keeps the approvals of the items it leaves
unchanged and drops the rest. v0.3 converts a v0.2 data folder when it first serves
it, with nothing approved; v0.2 then refuses that folder.

**The review door.** Every `mo push` now passes the door. The service compiles the
candidate in a child process, then lists its intent items and runs every promise,
service promise, example and test under a fixed plan: 200 inputs per function promise
and 1,000 sequences per service, inside 120 seconds of CPU and 180 seconds in all. A
failure is refused with E1433 and an unfinished plan with E1432. The review setting
then decides. Under `everything` every push is held. Under `intent` a push is held
unless it keeps every approved item, still calls the function each one is about from a
tool, a timer or the state initializer, and names no migration. A held push exits 3
with a review id while the old program keeps serving. Robert reads the intent
difference and the held source with `mo review --out`, and answers with `--yes ID` or
`--no ID`. A yes compiles and checks the candidate again before activating it. A later
held push replaces the earlier one, and any activation or approval makes a held one
stale. A service starts on `everything`, and only Robert changes the setting.

The codes new since v0.2.0 are E0107 and E1109 for service promises, and E1432 to E1437
for the plan, the checks, the credentials and the review.

## Retained limits

The lock does not protect against a shell on the service's host or write access to its
data folder: either is approval authority. Mo has no operating-system confinement, and
the check child runs candidate code under limits, not in a sandbox, so a memory-safety
defect in the compiler or the VM that pushed source can reach is a way around the door.
A change to a library module or the toolchain can change what an approved item means
while its digest stays the same, and so can a reorder of same-typed parameters under a
positional example row. A handler that still calls an approved function but ignores its
result keeps the item reached. Tests are not approved intent.

The door checks the same generated sequences on every push, so a defect outside them
passes every time. The strength rate rests on 12 wrong versions per half, a 95%
interval of about 65% to 98%, and says nothing about `submit`, `lease`, `acknowledge`,
`fail` or the anchors, which no wrong version could replace. `w11` survives under
`intent`: the `Done` filter of `list` also showing Dead jobs. Killing it needs an input
generator that reaches rarer states.

The planted changes and wrong versions are written cases, not real use. Process kills
do not establish power-loss durability, and the kill loop does not observe which
internal stage each kill lands in. Four fuzz targets ran fewer than 2,000 inputs in
their 300 seconds, `fuzz_protocol_server` only 116. The nightly does not run the
`models`, `cbmc` or `fuzz` groups; they run by hand at a phase boundary.

[live service runbook](../ops/live-service.md), and removing the development VM's
